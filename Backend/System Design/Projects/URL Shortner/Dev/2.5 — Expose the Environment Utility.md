# 2.5 — Expose the Environment Utility

## 1. What we're doing right now

We are updating `packages/common/src/index.ts` so the new environment utility becomes part of the **public API** of `@metriclink/common`.

## 2. Why this has to happen at this exact point

`env.ts` already exists and compiles, but other packages cannot cleanly consume it until `index.ts` exports it.

This preserves the intended boundary:

```text
service
   │
   │ import from @metriclink/common
   ↓
common/src/index.ts
   │
   ├── logger.ts
   └── env.ts
```

The service never needs to know where `createEnv()` is physically implemented.

## 3. Actual code

Update:

```text
packages/common/src/index.ts
```

to:

```typescript
export { createLogger } from "./logger.js";
export type { CreateLoggerOptions } from "./logger.js";

export type { Logger, LoggerOptions } from "pino";

// Environment
export { createEnv } from "./env.js";
export type {
  EnvOptions,
  EnvSchema,
} from "./env.js";
```

### What we have now

The public API of `@metriclink/common` contains:

```text
@metriclink/common
│
├── createLogger()
│
├── CreateLoggerOptions
├── Logger
├── LoggerOptions
│
├── createEnv()
├── EnvOptions
└── EnvSchema
```

This is the important distinction:

```text
internal implementation
        ↓
     index.ts
        ↓
   public package API
```

If we later rename or reorganize `logger.ts` or `env.ts`, consumers can continue importing from:

```typescript
import {
  createEnv,
  createLogger,
} from "@metriclink/common";
```

without depending on our internal folder structure.
