# 2.2 — Build the Shared Logger

## 1. What we're doing right now

We are creating the first reusable capability inside `@metriclink/common`: a `createLogger()` factory around **Pino**.

The logger will be configurable per service, so `url-service`, `analytics-service`, `auth-service`, etc. can all create their own named logger without duplicating Pino configuration.

## 2. Why this has to happen at this exact point

Pino is already installed in `@metriclink/common`, so the dependency required by this file now exists.

We build the logger **before the environment utility** because services will need logging throughout their startup and runtime infrastructure. More importantly, the logger is self-contained: it does not depend on configuration, database code, HTTP code, or any MetricLink feature.

The dependency remains one-way:

```text
pino
  ↓
common/logger.ts
  ↓
createLogger()
  ↓
MetricLink services
```

Create:

```text
packages/common/
└── src/
    └── logger.ts
```

## 3. Actual code

```typescript
import pino from "pino";
import type { Logger, LoggerOptions } from "pino";

export interface CreateLoggerOptions
  extends Omit<LoggerOptions, "name" | "transport"> {
  service: string;
  pretty?: boolean;
}

export const createLogger = (options: CreateLoggerOptions): Logger => {
  const { service, level = "info", pretty = false, ...rest } = options;

  const loggerOptions: LoggerOptions = {
    name: service,
    level,
    ...rest,
  };

  if (pretty) {
    loggerOptions.transport = {
      target: "pino-pretty",
      options: {
        colorize: true,
        translateTime: "SYS:standard",
      },
    };
  }

  return pino(loggerOptions);
};
```

### Understand the design

The important part is this interface:

```typescript
export interface CreateLoggerOptions
  extends Omit<LoggerOptions, "name" | "transport"> {
  service: string;
  pretty?: boolean;
}
```

We're reusing Pino's configuration rather than inventing our own complete logging API.

But we deliberately remove:

```text
name
transport
```

because **our common package owns those decisions**.

The service provides:

```typescript
createLogger({
  service: "url-service",
});
```

and the factory handles:

```text
service → Pino name
level   → Pino level
pretty  → development transport
```

The `...rest` is important because it still allows callers to provide other legitimate Pino options.

---

### Why `pretty` exists

Production logs should generally remain structured JSON because log aggregation systems can parse fields reliably.

Development output is easier to read when formatted.

So the intended distinction is:

```text
Development
    ↓
pretty: true
    ↓
human-readable logs

Production
    ↓
pretty: false
    ↓
structured JSON
```

One important detail: **`pino-pretty` is not installed yet.** That is intentional. The logger code supports the option, but we should add that development-only dependency before actually testing `pretty: true`.

For the first compilation check, we don't need the pretty transport.

## 4. What to check

First run TypeScript against the package:

```bash
pnpm --filter @metriclink/common exec tsc --noEmit
```

It should complete without TypeScript errors.

Then inspect:

```bash
pnpm --filter @metriclink/common exec tsc --showConfig
```

and confirm the package is using the inherited `tsconfig.base.json`.

### One subtle point

You may notice that TypeScript can compile `logger.ts` even though `pino-pretty` isn't installed.

That is because the `transport.target` value is simply a runtime configuration string. **If we actually create a logger with `pretty: true`, Pino will need `pino-pretty` available at runtime.**

For now, the required check is only:

```text
logger.ts
   ↓
TypeScript compilation
   ↓
PASS
```

**Stop here.** Once `tsc --noEmit` passes, we'll create `index.ts` and expose `createLogger()` as the public API of `@metriclink/common`.
