# 2.4 — Build the Shared Environment Utility

## 1. What we're doing right now

We are creating `packages/common/src/env.ts` with a reusable `createEnv()` function that validates environment variables using **Zod**.

This utility will be used later by MetricLink services such as `url-service`, `analytics-service`, and `auth-service`.

## 2. Why this has to happen at this exact point

Zod is already installed in `@metriclink/common`, so the dependency required by this utility exists.

More importantly, **environment validation belongs in the shared package** because every service needs the same basic behavior:

```text
process.env
    ↓
Zod schema
    ↓
validated + typed configuration
    ↓
service
```

Without this utility, every service would have to implement its own environment parsing and error handling, creating duplicated and inconsistent configuration logic.

Create:

```text
packages/common/src/env.ts
```

## 3. Actual code

```typescript
import { z, ZodObject, type ZodRawShape } from "zod";

/**
 * Optional configuration for environment validation.
 */
export interface EnvOptions {
  /**
   * Source of environment variables.
   * Defaults to `process.env` but can be overridden for testing.
   */
  source?: NodeJS.ProcessEnv;

  /**
   * Service name included in validation errors
   * to identify which application failed.
   */
  serviceName?: string;
}

/**
 * Validates environment variables against a Zod schema
 * and returns a fully typed configuration object.
 */
export function createEnv<TSchema extends ZodObject<ZodRawShape>>(
  schema: TSchema,
  options: EnvOptions = {},
): z.infer<TSchema> {
  const {
    source = process.env,
    serviceName = "service",
  } = options;

  const parsed = schema.safeParse(source);

  if (!parsed.success) {
    throw new Error(
      `[${serviceName}] Environment validation failed\n${parsed.error.message}`,
    );
  }

  return parsed.data;
}

/**
 * Helper type representing any valid Zod object schema.
 */
export type EnvSchema<TShape extends ZodRawShape> = ZodObject<TShape>;
```

### The important design

The generic is the key part:

```typescript
<TSchema extends ZodObject<ZodRawShape>>
```

It says:

> `createEnv()` accepts a Zod object schema.

Then:

```typescript
z.infer<TSchema>
```

extracts the TypeScript type represented by that schema.

For example, a service will eventually be able to write:

```typescript
const schema = z.object({
  PORT: z.coerce.number(),
  NODE_ENV: z.enum(["development", "production", "test"]),
});

const env = createEnv(schema);
```

TypeScript will understand that:

```text
env.PORT
```

is a number and:

```text
env.NODE_ENV
```

is the corresponding inferred union.

### Why `source` exists

Normally:

```typescript
source = process.env
```

means production code validates the actual process environment.

But tests can provide their own environment:

```typescript
createEnv(schema, {
  source: {
    PORT: "5000",
  },
});
```

This makes the utility **deterministic and testable** without modifying the real process environment.

### Why `safeParse()` instead of `parse()`?

`safeParse()` gives us structured validation results:

```text
success
   ├── true  → return validated data
   └── false → create service-specific error
```

That lets us produce an error such as:

```text
[URL_SERVICE] Environment validation failed
...
```

rather than exposing a generic validation failure without identifying which MetricLink service failed.
