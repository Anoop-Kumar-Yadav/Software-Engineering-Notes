# Lesson 18: Nx Cache Configuration

In the previous lesson, we learned that Nx can reuse the result of a task when its relevant inputs have not changed.

Now the important question is:

> How does Nx know which inputs belong to a task, and which generated files should be cached?

This is controlled through task cache configuration.

## 1. Why Cache Configuration Is Necessary

Consider this task:

Bash

```
nx build url-service
```

Nx needs to determine:

1. Which files affect the build?
    
2. Which configuration affects the build?
    
3. Which dependencies affect the build?
    
4. Which files are generated by the build?
    
5. Which generated files should be stored and restored?
    

Without knowing these details, Nx cannot reliably determine whether an old result can be reused.

Conceptually:

```
Task: url-service:build
        │
        ├── What affects the task?
        │      └── Inputs
        │
        └── What does the task produce?
               └── Outputs
```

Therefore, cache configuration mainly involves two concepts:

```
Inputs  → What Nx uses to identify the task
Outputs → What Nx stores as the task result
```

# 2. Inputs

An input is something that can influence the result of a task.

For a build task, possible inputs include:

- Source files.
    
- TypeScript configuration.
    
- Build configuration.
    
- Imported libraries.
    
- Package dependencies.
    
- Lockfile changes.
    
- Relevant environment variables.
    
- Workspace-level configuration.
    

For example:

```
url-service:build
```

may depend on:

```
apps/url-service/src/
libs/logger/
libs/config/
tsconfig.base.json
package.json
pnpm-lock.yaml
```

If one of these relevant inputs changes, the result of the build may also change.

The cache identity must therefore take those changes into account.

## 3. Example of Input Changes

Suppose `url-service` uses the shared `logger` library:

```
url-service ─────▶ logger
```

The source files may look like this:

```
apps/url-service/src/main.ts
libs/logger/src/lib/logger.ts
```

The application code may remain unchanged:

TypeScript

```
import { createLogger } from '@url-platform/logger';
```

But if the implementation of `logger` changes:

TypeScript

```
export function createLogger() {
  return {
    info(message: string) {
      console.log(`[URL-SERVICE] ${message}`);
    }
  };
}
```

then the effective build input of `url-service` may also change.

Conceptually:

```
logger changes
      │
      ▼
url-service build inputs change
      │
      ▼
Different cache identity
      │
      ▼
Previous url-service build result may not be reusable
```

This is why project dependencies matter when Nx evaluates task caching.

# 4. Outputs

An output is a file or directory generated by a task.

For example, a build may generate:

```
dist/apps/url-service/
```

with contents such as:

```
dist/apps/url-service/
├── main.js
├── package.json
└── assets/
```

These generated files are the task’s outputs.

Conceptually:

```
nx build url-service
        │
        ▼
Build executor
        │
        ▼
dist/apps/url-service/
```

Nx can store these outputs as part of the cached task result and restore them during a cache hit.

## 5. Inputs and Outputs Together

A task can be represented like this:

```
┌───────────────────────────────────────┐
│           url-service:build           │
├───────────────────────────────────────┤
│ Inputs                                │
│ ├── Application source files          │
│ ├── Shared library source files       │
│ ├── TypeScript configuration          │
│ ├── Build configuration               │
│ └── Relevant dependency information   │
├───────────────────────────────────────┤
│ Outputs                               │
│ └── dist/apps/url-service/            │
└───────────────────────────────────────┘
```

Nx uses the inputs to determine whether a previous result is valid.

Nx uses the outputs to know what generated artifacts belong to that result.

# 6. Conceptual `inputs` Configuration

A simplified target configuration may look like this:

JSON

```
{
  "targets": {
    "build": {
      "executor": "@nx/webpack:webpack",
      "inputs": [
        "default"
      ]
    }
  }
}
```

Here:

JSON

```
"inputs": ["default"]
```

means that the task uses the workspace’s configured default input set.

The exact default input behavior depends on the Nx workspace configuration and the plugins or presets being used.

The important idea is:

> `inputs` tells Nx which categories of information should be considered when determining whether a task result can be reused.

## 7. Conceptual `outputs` Configuration

A simplified build target may define its output directory:

JSON

```
{
  "targets": {
    "build": {
      "executor": "@nx/webpack:webpack",
      "outputs": [
        "{workspaceRoot}/dist/apps/url-service"
      ]
    }
  }
}
```

This indicates that the build produces output in:

```
dist/apps/url-service
```

The placeholder:

```
{workspaceRoot}
```

represents the root directory of the Nx workspace.

So this:

```
{workspaceRoot}/dist/apps/url-service
```

refers conceptually to:

```
url-platform/dist/apps/url-service
```

The exact output path must match the actual build configuration.

# 8. Why Outputs Matter During a Cache Hit

Consider this sequence:

Bash

```
nx build url-service
```

### First execution

```
Cache miss
    │
    ▼
Build executes
    │
    ▼
dist/apps/url-service/ is generated
    │
    ▼
Output is stored as part of the cached result
```

### Second execution

```
Cache hit
    │
    ▼
Nx reuses the cached result
    │
    ▼
Expected build output is restored or made available
```

If Nx did not know which files were outputs, it would not reliably know which generated artifacts should be restored when the cached result is reused.

Therefore:

```
Inputs  → Determine whether the result is still valid
Outputs → Identify what the task produced
```

# 9. Workspace-Level Cache Defaults

Instead of repeating the same cache configuration in every project, Nx allows common task behavior to be configured centrally.

For example, several applications may use the same build conventions:

```
api-gateway:build
url-service:build
auth-service:build
```

A workspace-level configuration can provide common defaults for all matching `build` targets.

Conceptually:

```
nx.json
└── targetDefaults
    └── build
        ├── Common inputs
        ├── Common outputs
        └── Common caching behavior
```

A simplified example:

JSON

```
{
  "targetDefaults": {
    "build": {
      "inputs": [
        "default"
      ],
      "cache": true
    }
  }
}
```

This expresses the idea that build targets should use a common input policy and participate in caching.

The exact supported properties and defaults depend on the Nx version and project configuration style.

# 10. Cache Configuration in the URL-Shortener Monorepo

Suppose your workspace contains:

```
apps/
├── api-gateway/
├── url-service/
└── auth-service/

libs/
├── logger/
├── config/
└── contracts/
```

A build task may be conceptually configured as follows:

```
api-gateway:build
    Inputs:
      - api-gateway source
      - contracts
      - logger
      - build configuration

    Outputs:
      - dist/apps/api-gateway/

url-service:build
    Inputs:
      - url-service source
      - contracts
      - logger
      - config
      - build configuration

    Outputs:
      - dist/apps/url-service/

auth-service:build
    Inputs:
      - auth-service source
      - contracts
      - logger
      - config
      - build configuration

    Outputs:
      - dist/apps/auth-service/
```

Each task has its own input set and output set.

Therefore, Nx can cache them independently:

```
api-gateway:build  → Cache entry A
url-service:build  → Cache entry B
auth-service:build → Cache entry C
```

A change to `url-service` does not automatically invalidate the build result of every unrelated project. However, projects that depend on changed libraries may need to be rebuilt.

# 11. Cacheable and Non-Cacheable Tasks

A task is generally suitable for caching when:

- Its result depends on known inputs.
    
- The same inputs produce the same result.
    
- Its outputs can be identified.
    
- Reusing the result does not skip a required side effect.
    

Typical cacheable tasks include:

```
build
test
lint
type-check
```

Some tasks may not be suitable for caching:

```
deploy
publish
send-notification
database-reset
```

For example:

Bash

```
nx run url-service:deploy
```

may upload files, restart containers, or change a remote environment.

Reusing an old deployment result would not necessarily perform the deployment again.

Therefore, caching should not be enabled indiscriminately.

# 12. The Complete Flow

```
nx build url-service
        │
        ▼
Nx identifies the task
        │
        ▼
Nx determines configured inputs
        │
        ▼
Nx checks whether the inputs match a previous execution
        │
        ├── Matching result exists
        │       │
        │       ▼
        │   Cache hit
        │       │
        │       ▼
        │   Restore or reuse outputs
        │
        └── No matching result
                │
                ▼
            Cache miss
                │
                ▼
          Execute build
                │
                ▼
          Generate outputs
                │
                ▼
       Store result in cache
```

## Key takeaway

```
Inputs:
  Determine what can affect a task’s result.

Outputs:
  Identify what the task generates.

Cache configuration:
  Tells Nx how to evaluate task validity and what artifacts
  belong to the cached result.
```

For the URL-shortener monorepo:

```
url-service:build
    Inputs  → Source, libraries, configuration, dependencies
    Outputs → dist/apps/url-service/
```
