
We now have 16 URL shards, and the average peak load is approximately:

```text
578,500 redirects/sec
──────────────────────
       16 shards

≈ 36,156 redirects/sec/shard
```

That looks healthy against our assumed `40,000 QPS/shard` benchmark. But **average distribution is not enough** for a URL shortener. Route.io has a potentially severe **hot-key problem** because traffic is distributed by `shortCode`, while user traffic is distributed by popularity.

## 7.55 The Problem With Uniform Sharding

Suppose:

```text
100M URLs
16 shards
```

Hash-based sharding gives us approximately:

```text
6.25M URLs/shard
```

But assume the traffic distribution follows a realistic long-tail pattern:

```text
Top 1% of URLs
→ 50% of all redirects
```

Then:

```text
578,500 peak redirects/sec × 50%
≈ 289,250 redirects/sec
```

are generated by only the hottest 1% of URLs.

Those URLs are still distributed according to their `shortCode`.

So imagine one particularly viral URL receives:

```text
200,000 redirects/sec
```

and its hash maps it to:

```text
Shard 7
```

Now:

```text
Shard 7
    ↓
200,000 QPS for one URL
```

while the other shards may be operating around:

```text
~25K–40K QPS
```

This means the sharding strategy successfully distributed **data**, but failed to distribute **traffic**.

That distinction is extremely important in an interview.

---

# 7.56 Why More Shards Are Not the Correct Solution

You might initially think:

> "Let's increase from 16 shards to 64."

That does not reliably solve this problem.

The hot URL still has exactly one `shortCode`.

For example:

```text
hash("abc123") % 64 = 37
```

So all requests for:

```text
GET /abc123
```

still go to:

```text
Shard 37
```

Increasing the number of shards changes **where** the hot key lives, not how many machines serve that hot key.

This gives us the next bottleneck:

```text
Dataset distribution ≠ traffic distribution
```

We need a mechanism that allows the same URL result to be served without repeatedly accessing the database.

---

# 7.57 Architectural Change #4 — Cache the URL Resolution

Now we can finally justify introducing a **distributed cache**, such as Redis.

The important reason is not:

> "URL shorteners use Redis."

The reason is:

> **A small number of hot URL keys are generating a disproportionate amount of read traffic against the database.**

The new redirect path becomes:

```text
Client
   |
   v
Load Balancer
   |
   v
Node.js
   |
   v
Redis
   |
   +── HIT ──────> destination URL
   |
   +── MISS
          |
          v
       URL Shard
          |
          v
       PostgreSQL
```

---

# 7.58 Cache Lookup Sequence

For:

```text
GET /abc123
```

Node.js first executes:

```text
GET url:abc123
```

against Redis.

### Cache hit

If Redis contains:

```text
url:abc123
→ https://example.com/article
```

then:

```text
Redis
  ↓
destination URL
  ↓
Node.js
  ↓
302 Found
```

PostgreSQL is completely bypassed.

### Cache miss

If Redis returns:

```text
nil
```

then:

```text
Node.js
   ↓
hash(shortCode)
   ↓
Shard 7
   ↓
PostgreSQL
   ↓
destination URL
```

Node.js then populates Redis:

```text
SET url:abc123 destination EX 3600
```

and returns:

```text
302 Found
```

So the normal path becomes:

```text
Cache hit:
Client → Node.js → Redis → 302

Cache miss:
Client → Node.js → Redis → PostgreSQL → Redis → 302
```

---

# 7.59 Why This Changes the Capacity Calculation

Suppose:

```text
578,500 peak redirects/sec
```

and our cache achieves:

```text
95% hit ratio
```

Then:

```text
578,500 × 95%
≈ 549,575 requests/sec
```

are served directly from cache.

Only:

```text
578,500 × 5%
≈ 28,925 requests/sec
```

reach PostgreSQL.

Compare this with the previous architecture:

```text
Before cache:

PostgreSQL
≈ 578,500 lookup requests/sec
```

After cache:

```text
PostgreSQL
≈ 28,925 lookup requests/sec
```

That's a **20× reduction** in database lookup traffic.

This is the quantitative justification for the cache.

---

# 7.60 What Happens to Our Shards?

Previously:

```text
578,500 / 16
≈ 36,156 QPS/shard
```

After a 95% cache hit ratio:

```text
28,925 / 16
≈ 1,808 QPS/shard
```

So the database workload becomes dramatically smaller.

However, this does **not** mean we remove the shards.

Why?

Because the cache is not the source of truth.

The authoritative mapping remains:

```text
PostgreSQL shard
```

Redis contains a derived copy:

```text
shortCode → destination URL
```

Therefore:

```text
PostgreSQL
    ↓
source of truth

Redis
    ↓
performance layer
```

If Redis disappears, Route.io must still be able to resolve URLs from PostgreSQL.

---

# 7.61 Cache-Aside Strategy

For Route.io, the natural initial strategy is **cache-aside**.

The flow is:

```text
                 ┌───────────────┐
                 │    Node.js    │
                 └───────┬───────┘
                         │
                         ▼
                  ┌─────────────┐
                  │    Redis    │
                  └──────┬──────┘
                         │
                  ┌──────┴──────┐
                  │             │
                 HIT           MISS
                  │             │
                  │             ▼
                  │       PostgreSQL
                  │             │
                  │             ▼
                  │          Redis SET
                  │             │
                  └──────┬──────┘
                         ▼
                    Destination
```

This works particularly well because our workload is overwhelmingly read-heavy.

Our URL mapping has approximately:

```text
~1,000 redirects
        :
~1 URL creation
```

at this scale.

That means a URL that enters the cache can potentially serve thousands of reads before the cache needs to be refreshed.

---

# 7.62 What About URL Updates?

This is where cache invalidation becomes a real engineering problem.

Suppose:

```text
PostgreSQL:
abc123 → https://old.example.com

Redis:
abc123 → https://old.example.com
```

The user updates the destination:

```text
abc123
    ↓
https://new.example.com
```

PostgreSQL becomes:

```text
abc123 → https://new.example.com
```

But Redis still contains:

```text
abc123 → https://old.example.com
```

If we don't invalidate it, redirects continue going to the old destination.

Therefore the write path must handle cache invalidation.

For example:

```text
UPDATE URL
    ↓
PostgreSQL
    ↓
invalidate Redis key
    ↓
url:abc123
```

The next redirect becomes:

```text
Redis MISS
    ↓
PostgreSQL
    ↓
new destination
    ↓
Redis SET
```

This gives us a clean source-of-truth model.

---

# 7.63 TTL

We should also assign a TTL to cached URL records.

For example:

```text
TTL = 1 hour
```

Then:

```text
SET url:abc123 https://example.com EX 3600
```

After one hour, Redis removes the entry automatically.

This protects us from permanently stale values if invalidation fails.

The tradeoff is:

```text
Short TTL
→ fresher data
→ more PostgreSQL misses

Long TTL
→ higher cache hit ratio
→ greater stale-data window
```

For a redirect platform, we might choose a longer TTL for immutable or rarely updated URLs and a shorter TTL for frequently modified URLs.

---

# 7.64 Expiration Creates Another Important Case

Route.io supports optional URL expiration.

Suppose:

```text
expiresAt = 2026-08-19 12:00:00
```

and Redis contains:

```text
url:abc123
→ destination
TTL = 1 hour
```

We must ensure the cache doesn't return an expired URL.

There are two common safeguards:

```text
1. Store expiresAt in the cached value and validate it.
2. Set the Redis TTL to no later than the URL's expiration time.
```

For example:

```text
Redis TTL
=
min(
    normal cache TTL,
    expiresAt - currentTime
)
```

So if the URL expires in 10 minutes:

```text
normal cache TTL = 1 hour
URL expiration   = 10 minutes

actual Redis TTL = 10 minutes
```

This keeps cache behavior aligned with Route.io's functional requirement.

---

# 7.65 New Scale Ceiling

Suppose our Redis cluster can sustain:

```text
1,000,000 GET operations/sec
```

and our application fleet can scale horizontally.

Our peak redirect workload:

```text
578,500 requests/sec
```

is comfortably below that assumed cache capacity.

Meanwhile PostgreSQL receives approximately:

```text
28,925 lookup/sec
```

with a 95% hit ratio.

So the redirect architecture's practical capacity has increased substantially.

Under these assumptions, we can support **100M users and ~578K peak redirects/sec** without requiring the PostgreSQL shards to process every redirect.

---

# 7.66 But There Is a New Failure Mode

Distributed caching introduces a different problem:

## Cache stampede

Suppose a very hot URL has:

```text
200,000 requests/sec
```

and its Redis key expires.

Immediately:

```text
200,000 requests
       ↓
Redis MISS
       ↓
200,000 PostgreSQL queries
```

We have just converted a cache success into a database spike.

This is called a **cache stampede** or **thundering herd**.

For a normal URL this might be harmless.

For a hot URL:

```text
200,000 QPS
```

it can overwhelm the shard.

---

# 7.67 Preventing the Stampede

A common solution is **request coalescing / single-flight**.

Conceptually:

```text
Request 1 ──┐
Request 2 ──┤
Request 3 ──┤
Request 4 ──┤
             ├── Redis MISS
Request N ──┘
                ↓
          One PostgreSQL lookup
                ↓
          Populate Redis
                ↓
        All requests receive result
```

Instead of:

```text
100,000 misses
→ 100,000 database queries
```

we want:

```text
100,000 misses
→ 1 database query
→ Redis SET
→ 100,000 responses
```

The exact implementation can use an application-level single-flight mechanism or a distributed locking strategy depending on the deployment topology.

At this scale, you must also consider that Node.js instances are separate processes, so an **in-process lock alone is insufficient** to coordinate requests across the entire fleet.

---

# 7.68 Cost of Introducing Redis

We solved a major bottleneck, but introduced another distributed system.

|Cost|Consequence|
|---|---|
|Redis infrastructure|Additional compute and memory|
|Cache invalidation|Updates must invalidate cached values|
|Stale data|TTL creates a possible stale window|
|Cache stampede|Requires protection for hot keys|
|Memory sizing|Hot URL working set must fit in memory|
|Failure handling|Redis outage must fall back to PostgreSQL|
|Operational complexity|Another cluster to monitor|
|Serialization|Cached representation must be defined|

The key point is:

**Redis is now justified because the measured workload contains hot keys that create concentrated database traffic.**

We did not need it at 100K users simply because caching is "best practice."

The redirect path is now:

```text
                                  Internet
                                     |
                                     ▼
                            ┌─────────────────┐
                            │  Load Balancer  │
                            └────────┬────────┘
                                     |
                         ┌───────────┼───────────┐
                         ▼           ▼           ▼
                      Node.js     Node.js     Node.js
                         │           │           │
                         └───────────┼───────────┘
                                     |
                                     ▼
                              ┌─────────────┐
                              │    Redis    │
                              │   Cluster   │
                              └──────┬──────┘
                                     |
                            ┌────────┴────────┐
                            │                 │
                           HIT               MISS
                            │                 │
                            │                 ▼
                            │          Shard Router
                            │                 |
                            │       ┌─────────┼─────────┐
                            │       ▼         ▼         ▼

The transactional and analytics paths remain:

   ↓

Analytics
   ↓
Message queue
   ↓
Analytics consumers
   ↓
Analytics storage
```

So Route.io now has **three major runtime paths**:

```text
Redirect:
Client → LB → Node.js → Redis → PostgreSQL shard on miss

Transactional:
Client → LB → Node.js → PostgreSQL

Analytics:
Redirect → Queue → Analytics consumers → Analytics storage
```

# 7.70 Current Scale Evolution

|Scale|Bottleneck|Change|Result|
|---|---|---|---|
|≤100K|Basic resource limits|Node.js + PostgreSQL|Simple V1|
|~1M|Node.js CPU/event loop|Horizontal Node.js scaling|Application scale-out|
|~10M|PostgreSQL read pressure|Read replicas|Read scale|
|~10M|Analytics writes/storage|Message queue + analytics consumers|Analytics isolation|
|~100M|Single logical DB scaling domain|Database sharding|Dataset/throughput partitioning|
|~100M|Hot URLs concentrate traffic|Redis cache|Hot-key read offload|

The architecture is now considerably more complex than V1, but every major component has a specific workload trigger.

# 7.71 The Next Bottleneck

There is an important consequence of introducing Redis.

We have solved:

```text
Database read amplification
```

but we haven't solved **global traffic spikes**.

Consider a viral URL:

```text
1,000,000 redirects/sec
```

Even with Redis, the system must now handle:

```text
1M Redis GET/sec
1M Node.js requests/sec
1M HTTP responses/sec
```

And potentially:

```text
1M × response/network bytes
```

of outbound traffic.

If the redirect response is approximately:

```text
500 bytes
```

then:

```text
1,000,000 × 500 bytes
= 500 MB/sec
```

of outbound response traffic.

That's:

```text
≈ 4 Gbps
```

for one million redirects per second.

Now we're looking at a different resource:

**network and edge capacity.**

This is where a CDN or edge caching strategy may finally become justified.

But before adding one, the next calculation should be:

> **How much of Route.io's redirect traffic can actually be served from the edge, and what consistency/expiration constraints prevent us from doing so?**

That is the next architectural boundary.
